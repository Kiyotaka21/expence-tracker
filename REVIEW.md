# Code review

Правила ревью pull request в этом репозитории. Процесс ветвления, формат коммитов и требования к телу PR — в корневом [CLAUDE.md](CLAUDE.md); предметные тонкости бэкенда и фронтенда — в [apps/api/CLAUDE.md](apps/api/CLAUDE.md) и [apps/web/CLAUDE.md](apps/web/CLAUDE.md). Здесь — что проверяет ревьюер, в каком порядке и что замечанием не считается.

**CI нет.** Единственный барьер перед `main` — руки автора и глаза ревьюера. Поэтому ревью читает не только дифф, но и то, что автор написал о проверках: непрогнанные `pnpm typecheck`, `pnpm lint`, `pnpm build` здесь никто не поймает автоматически.

## Что делает автор до открытия PR

- Прогнал `pnpm typecheck`, `pnpm lint`, `pnpm build` — и перечислил это в теле PR явно. Молчание ревьюер прочтёт как «проверено», и это худший из возможных вариантов.
- Прочитал свой дифф целиком. Отладочные `console.log`, закомментированный код, `.env` (кроме `*.example`), `dist`, `.next`, `.turbo`, `apps/api/src/generated` в индекс не попадают.
- Заголовок PR — по правилам заголовка коммита: `<тип>(<область>): <что делает>`, до 72 символов, императив, с маленькой буквы, без точки.
- Тело PR отвечает на «зачем»: решения, которых не видно в диффе, что отвергнуто и почему, как проверяли, что осталось вне объёма.

Ревьюер вправе вернуть PR не читая дифф, если тело пустое, `--fill` подставил описание одного коммита вместо описания работы или в PR смешаны две несвязанные фичи.

## Порядок чтения

Сверху вниз по радиусу поражения — так ошибка находится там, где её дешевле исправить:

1. **Тело PR** — что автор считал задачей. Дифф читается уже с этой гипотезой.
2. **`packages/contracts`** — форму запроса и ответа видят сразу оба приложения.
3. **`apps/api/prisma`** — миграции необратимы на чужих машинах.
4. **`apps/api/src`**, затем **`apps/web/src`** — потребители контракта.

Если в PR правится контракт, а второй стороны в диффе нет, дальше читать нечего: коммит по определению неполный. `contracts` компилируется в `dist`, и половинчатая правка ломает и API, и веб.

## Уровни замечаний

Помечайте каждое замечание — иначе автор угадывает, что блокирует влитие, а что мысли вслух:

| Метка      | Что значит                                                     |
| ---------- | -------------------------------------------------------------- |
| `blocker`  | Влить нельзя: ломает сборку, контракт, данные или безопасность |
| `fix`      | Поправить в этом PR, но не страшно                             |
| `nit`      | Вкусовое, автор решает сам; не повод держать PR                |
| `question` | Не понял замысел, ответ может снять замечание                  |

Замечание формулируется как «файл:строка + что не так + почему», а не «перепиши». «Сумма отдаётся числом — по пути к клиенту станет float, нужна строка через `toFixed(2)` в маппере» проверяется и обсуждается; «здесь неправильно» — нет.

`blocker` без объяснения «почему» не блокирует: у ревьюера есть право остановить PR, но нет права не объяснять.

## Чеклисты

### Контракты (`packages/contracts`)

- DTO описаны zod-схемой в контрактах, а не руками в модуле. В API схема оборачивается `createZodDto`, в вебе идёт в `zodResolver` — обе стороны читают один источник.
- Любая правка формы запроса или ответа — **ломающее изменение**: `feat(contracts)!: …` и абзац `BREAKING CHANGE:` в футере. Не «если сломается»: оба приложения читают эту схему сразу.
- Обе стороны правки — в одном коммите. Отдельный коммит «сначала контракт» не собирается.
- `class-validator` в проекте не используется; появился в диффе — `blocker`.

### Миграции Prisma (`apps/api/prisma`)

- Миграция едет в том же коммите, что и код, который её использует.
- Переименование модели или колонки Prisma разворачивает в `DROP` + `CREATE`. Такое в диффе миграции — `blocker`: нужен `--create-only` и `ALTER TABLE … RENAME` руками (образец — `expenses_to_transactions`).
- В описании проверок порядок: `pnpm db:migrate`, затем `pnpm db:generate`. `migrate dev` в Prisma 7 клиент не генерирует, а `generate` до миграции научит клиент селектить колонку, которой нет в БД.
- Сгенерированный клиент (`apps/api/src/generated`) в диффе — `blocker`, он в `.gitignore`.
- Деньги — `Decimal(12,2)`. Новое денежное поле другого типа обсуждается до влития, а не после.

### API (`apps/api`)

- Доступ закрыт по умолчанию (`JwtAuthGuard` глобально). Каждый новый `@Public()` — точка внимания ревьюера: почему маршрут открыт.
- Выборки и правки — только по `@CurrentUser()`. Запрос, которым можно достать чужую строку по `id` из параметров, — `blocker`.
- Сущности приводятся к форме контракта в `*.mapper.ts` (`Date` → ISO-строка, `amount.toFixed(2)`). Валидация ответов (`ZodSerializerInterceptor`) выключена сознательно — маппер никто не подстрахует, кроме ревьюера.
- Сумма наружу — **строкой**. Число в ответе — `blocker`.
- Импорты только относительные: path-алиасов в `apps/api` нет, `nest build` их не переписывает.
- `src/generated/prisma` импортируют только `PrismaService` и `UsersRepository`. Новый импорт сгенерированных типов в маппере или контроллере — `fix`: мапперы работают со структурными `*Like`-интерфейсами.
- Слой репозитория выделен только у `users`. Требовать репозиторий в новом модуле — `nit`, а не `blocker`: неоднородность здесь осознанная.
- Русский текст ошибок 401 и 409 — часть контракта с вебом, он показывает их как есть. Меняете текст — смотрите, не ждёт ли его фронтенд дословно.

### Веб (`apps/web`)

- Импорты только вниз по слоям (`app` → `views` → `widgets` → `features` → `entities` → `shared`) и только через `index.ts` среза. Импорт в соседний срез того же слоя запрещён — общий код опускается слоем ниже.
- Правило проверяет `no-restricted-imports` в `apps/web/eslint.config.mjs`. **`eslint-disable` на этом правиле — предмет обсуждения в PR, а не деталь реализации:** либо срез лежит не в том слое, либо общий код пора опустить ниже.
- `shared` импортируется по модулям (`@/shared/ui/button`), барреля у него нет намеренно. Появившийся `shared/index.ts` — `blocker`.
- Экран собирается в `views/<slice>/ui/<slice>-page.tsx`, `page.tsx` роутера — тонкая обёртка с `metadata`. Логика в `page.tsx` — `fix`.
- Формы — `field` + `Controller` + контрактная схема. Компонента `form` в стиле `radix-nova` нет, самодельный аналог — `fix`.
- После `shadcn add` версии в `apps/web/package.json` закреплены точно: CLI ставит их с кареткой. Каретка в диффе — `blocker`.
- Свои в `shared/ui` — `error-alert.tsx` и `password-input.tsx`. Если они в диффе изменились «сами», их затёр `shadcn add --overwrite`.
- Арифметики над суммами на клиенте нет: API отдаёт строку, форматирование — через `shared/lib/format`.
- Любой редирект по пути из URL проходит через `safeInternalPath` — иначе открытый редирект.
- Запросы к API идут через `shared/api/client.ts`. Прямой `fetch` в компоненте — `blocker`: мимо клиента не работают refresh и `ApiError`.

### Зависимости и версии

- Версии закреплены точно, без `^`, во всех `package.json`.
- TypeScript остаётся на 5.9.3, ESLint — на 9.39.5. Bump любого из них в PR, который занимается другим, — `blocker`: TS двигается только вместе с мажором typescript-eslint, а ESLint 10 ломает линт веба целиком.
- Новая зависимость обосновывается в теле PR. Не обоснована — `question`, и до ответа PR не вливается.
- Правки `pnpm-workspace.yaml` (`onlyBuiltDependencies`, `ignoredBuiltDependencies`) и корневых devDependencies читаются отдельно: `prettier-plugin-tailwindcss` из корня убирать нельзя, иначе `pnpm format` падает на файлах веба.
- `pnpm-lock.yaml` в диффе есть, если зависимости менялись, и отсутствует, если не менялись.

### История и влитие

- Один PR — одна законченная фича. Разросся — дробится на ветки, а не вливается «пока так».
- Ветка обновлена ребейзом от свежего `main`, merge-коммитов в диффе нет.
- Влитие — «Rebase and merge»: коммиты по конвенции осмысленные, схлопывать их незачем. «Squash and merge» — только для черновой истории с `wip`-коммитами.
- После влития ветка удаляется и на GitHub, и локально.

## Что замечанием не считается

- **Форматирование.** Его делает `pnpm format`; замечания про отступы и переносы — шум. Формат разъехался — просят прогнать команду, а не переставляют пробелы в комментариях.
- **Стиль импортов и всё, что ловит ESLint.** Линт зелёный — вопрос закрыт.
- **Отсутствие тестов.** Тестового раннера в проекте нет сознательно. Требовать тесты в PR с фичей нельзя: раннер заводится отдельным решением и отдельным PR. «Это стоило бы покрыть, когда раннер появится» — `nit`, не более.
- **Отсутствие CI-проверок в PR.** CI нет; перечисленные автором прогоны — то, что его заменяет.
- **Неоднородность слоя репозитория** в `categories` и `transactions` и прямой доступ к `refresh_sessions` из `AuthService` — известные решения, а не недосмотр.
- **Блок `nextjs-agent-rules` в `apps/web/AGENTS.md`** — его пишет сам `next dev`, удалять его из диффа бесполезно.
- **Тема.** Переключателя темы в интерфейсе нет намеренно, тема следует настройке ОС.

## Ответ автора на ревью

- Правки по ревью — обычные коммиты в ту же ветку и `git push`: PR обновляется сам. Переписывать историю опубликованной ветки ради красоты не нужно; пришлось — `--force-with-lease`, никогда просто `--force`.
- На каждое замечание — либо правка, либо ответ, почему нет. Молча закрытый тред читается как «сделано», и это возвращается на следующем ревью.
- Замечание, признанное верным и относящееся ко всему репозиторию, дописывается в памятку (`CLAUDE.md` нужного приложения или этот файл) тем же PR. Иначе то же самое ловится в третий раз.

## Инструменты

`gh` установлен, но не в PATH — ни Git Bash, ни PowerShell его не видят. Вызываем по полному пути, тело ревью передаём файлом (в нём markdown со списками и кодом, в одной строке аргумента он разъезжается); файл держим вне репозитория:

```bash
GH='/c/Program Files/GitHub CLI/gh.exe'

"$GH" pr list
"$GH" pr view 12 --comments          # тело PR и обсуждение
"$GH" pr diff 12                     # дифф целиком
"$GH" pr checkout 12                 # локально: pnpm typecheck && pnpm lint && pnpm build

"$GH" pr review 12 --comment --body-file /path/to/review.md
"$GH" pr review 12 --request-changes --body-file /path/to/review.md
"$GH" pr review 12 --approve --body 'проверки прогнал локально, замечаний нет'
```

Ревьюер, у которого дифф не читается без запуска, забирает ветку через `pr checkout` и прогоняет `pnpm typecheck`, `pnpm lint`, `pnpm build` сам. Это единственный способ проверить утверждение автора, что проверки зелёные.
