# Коммит в ветку

Процедура одного коммита: ветка → что входит в коммит → проверки → сообщение → пуш.

Коммитим только когда попросили, пушим — отдельным шагом и тоже по запросу.

## 1. Ветка

```bash
git branch --show-current
git status --short
```

**В `main` не коммитим напрямую.** Правка документации — тоже ветка: `main` остаётся
веткой, в которую только вливают. Если оказались на `main` — сначала ветка:

```bash
git switch main && git pull --ff-only        # стартуем всегда со свежего main
git switch -c feature/web-landing-page
```

Незакоммиченные изменения `git switch -c` перенесёт в новую ветку — терять нечего.

- **Имя**: `<тип>/<область>-<что>`, латиница, kebab-case. Область опускаем, когда правка
  задевает весь репозиторий.
- **Тип фичи в ветке пишется полным словом**: ветка `feature/…`, коммит `feat: …` —
  Conventional Commits допускает в заголовке только `feat`, у ветвей такого ограничения
  нет. Остальные типы совпадают: `fix/`, `refactor/`, `perf/`, `docs/`, `chore/`.
- Примеры: `feature/api-monthly-report`, `fix/web-refresh-race`, `chore/deps-bump-prisma`,
  `docs/api-transactions-jsdoc`.
- Одна ветка — одна законченная фича и один PR. Разрослась — дробим на несколько ветвей.

## 2. Что входит в коммит

**Один коммит — одна законченная единица работы.** Критерий простой: коммит должен
собираться сам по себе.

- Миграция Prisma едет вместе с кодом, который её использует.
- Правка схемы в `packages/contracts` — вместе с обеими сторонами, которые её читают:
  `contracts` компилируется в `dist`, и половинчатое изменение ломает и API, и веб.
- Документация едет в том же коммите, а не отдельным заходом «потом»: `.claude/docs/*`
  (новая ручка → `api.md`, новое поле → ещё и `database.md`, новый слой или зависимость
  между пакетами → `architecture.md`, новая команда или порядок работы →
  `developer-guide.md`; таблица целиком — в разделе «Обновление docs» корневого
  CLAUDE.md), а для правок в `apps/api` — JSDoc и Swagger-декораторы.
- Работы больше, чем на одну единицу, — режем на несколько коммитов, а не сваливаем
  в один.

**Что не должно попасть в индекс** (всё в `.gitignore`, но `git status --short` перед
`git add` смотрим): `.env*` кроме `*.example`, `dist`, `.next`, `.turbo` и сгенерированный
`apps/api/src/generated`.

Два источника лишних файлов в диффе:

- `pnpm format` форматирует весь репозиторий. Зацепил файлы, которых вы не касались, —
  не тащите их в коммит: `git add` по своим путям, а не `git add -A` не глядя.
- `apps/web/AGENTS.md` дописывает сам `next dev` — блок `nextjs-agent-rules`
  восстанавливается при каждом запуске. В коммит с вашей работой он не идёт.

## 3. Проверки перед коммитом

CI нет, поэтому единственный барьер — руки:

```bash
pnpm typecheck && pnpm lint && pnpm build
```

Не проходит — починили и прогнали снова, а не закоммитили. `--no-verify` не используем.

## 4. Сообщение

Формат — [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/), текст
по-русски:

```
<тип>(<область>): <что делает коммит>

<зачем это нужно: ограничения, отвергнутые альтернативы, подводные камни>

<BREAKING CHANGE и ссылки — если есть>

Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>
```

- **Типы**: `feat`, `fix`, `refactor`, `perf`, `docs`, `style`, `test`, `build`, `ci`,
  `chore`, `revert`.
- **Области**: `api`, `web`, `contracts`, `config` (пресеты eslint/tsconfig), `deps`.
  Область опускается, когда правка задевает весь репозиторий целиком, и берётся по
  преобладающей части диффа: коммит, где заодно правились сиды и документация, но основная
  работа в вебе, остаётся `feat(web)`, а не теряет область.
- **Заголовок**: до 72 символов, императив («добавить», «починить»), с маленькой буквы,
  без точки в конце.
- **Тело объясняет «зачем», а не «что»** — «что» видно в диффе. Здесь место решениям и
  границам: почему версия закреплена, почему миграция сделана через `--create-only`, почему
  сумма отдаётся строкой. Абзацами, с переносом по ~72 символа — так набрана вся история.
- **Ломающее изменение** помечается `!` перед двоеточием (`feat(contracts)!: …`) и абзацем
  `BREAKING CHANGE: …` в футере. Для `contracts` ломающей считается любая правка формы
  запроса или ответа: её видят сразу оба приложения.
- **Трейлер `Co-Authored-By`** — последней строкой, отдельным абзацем. Так оформлена вся
  агентская история репозитория.

**Многострочное сообщение передаём файлом.** Кавычки и переносы в PowerShell и Git Bash
ведут себя по-разному, поэтому текст пишем в файл в скрэтчпаде (вне репозитория — в индекс
он попадать не должен) и коммитим им:

```bash
git commit -F /path/to/scratchpad/commit-msg.txt
```

Заголовки из истории для ориентира:

```
feat(api): добавить транзакции с фильтрами и сводкой за месяц
feat(web): добавить экраны входа и регистрации с защитой маршрутов
chore(config): добавить общие пресеты tsconfig и eslint
docs: требовать актуализации .claude/docs при добавлении функционала
```

## 5. Пуш

Отдельный шаг: пушим, только если попросили.

```bash
git push -u origin feature/web-landing-page
```

- **Ветку обновляем ребейзом**, не merge-коммитом — история линейная:
  `git pull --rebase origin main`, дальше `git push --force-with-lease`, никогда просто
  `--force`.
- Историю опубликованной ветки не переписываем ради красоты. Правки по ревью — обычные
  коммиты в ту же ветку и `git push`: PR обновляется сам.
- Дальше PR — раздел «Pull request» корневого [CLAUDE.md](../../../CLAUDE.md): `gh` не в
  PATH, тело передаётся файлом.

## Чего не делаем

- Коммит прямо в `main` — включая правку документации.
- Коммит с падающими `pnpm typecheck`, `pnpm lint`, `pnpm build`, обход хуков
  (`--no-verify`).
- `git add -A` без взгляда на `git status --short`.
- `git commit --amend` и ребейз опубликованной ветки без `--force-with-lease`.
- `wip`-коммиты в ветке, которая пойдёт в PR: вливаем через «Rebase and merge», значит
  каждый коммит виден в `main` и должен быть осмысленным.
