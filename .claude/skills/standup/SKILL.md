# Отчёт для стендапа

Собрать всё, что сделано за вчерашний день, и напечатать готовый к зачитыванию отчёт.

**Скилл только читает.** Ничего не коммитим, не пушим, не мержим, файлы репозитория не
меняем — даже если по ходу видно, что что-то стоит поправить: это отдельная работа и
отдельная просьба.

## 1. Период

По умолчанию — **вчерашний календарный день по локальному времени**. Аргумент меняет
период: `/standup 2026-08-28` — конкретная дата, `/standup 3d` — последние три дня.

```bash
DAY=$(date -d yesterday +%F)          # или дата из аргумента
NEXT=$(date -d "$DAY +1 day" +%F)
```

**Пустой период — не повод для пустого отчёта.** Выходные, отпуск, день без коммитов:
находим последний день с активностью и отчитываемся за него, назвав дату в заголовке
прямым текстом.

```bash
git log --all -1 --format='%ad' --date=short
```

Молча подменять период нельзя: человек на стендапе назовёт вчерашнюю дату вслух.

## 2. Сбор данных

Сначала подтягиваем чужую работу — иначе видны только локальные ветки:

```bash
git fetch --all --prune --quiet
```

### Коммиты

```bash
git log --all --no-merges --since="$DAY 00:00" --until="$NEXT 00:00" \
  --format='%h | %an | %ad |%d %s' --date=format:'%F %H:%M'
```

- **`--all`, а не `main`.** Работа дня лежит в ветке под PR, в `main` она попадает позже —
  по `main` вы отчитаетесь за позавчера.
- **`--no-merges`.** Merge-коммит не работа; факт влития берётся из PR (ниже).
- **Своя работа — детально, чужая — одной строкой.** Кто «свой», берём из репозитория, а
  не из головы: `git config user.name`, `git config user.email`. Чужие коммиты в отчёте
  нужны как контекст («в `main` влилось вот это»), а не как ваш пересказ чужого дня.

Деталь по каждому коммиту:

```bash
git show -s --format='%h | %an | %ad%n%s%n%n%b' --date=format:'%F %H:%M' <sha>
git show --stat --format='' <sha>
```

**Тело коммита — единственный источник «зачем».** В этом репозитории оно обязательно и
объясняет решения, ограничения и отвергнутые альтернативы: в отчёт идёт именно оно, а не
пересказ заголовка другими словами. Тело пустое — так и пишем («мотивация в коммите не
записана»), догадки о причинах не сочиняем.

### Pull request

`gh` установлен, но не в PATH:

```bash
GH='/c/Program Files/GitHub CLI/gh.exe'

"$GH" pr list --state merged --search "merged:$DAY..$NEXT" \
  --json number,title,author,mergedAt,url
"$GH" pr list --state all --search "created:$DAY..$NEXT" \
  --json number,title,author,createdAt,state,url
"$GH" pr list --state open \
  --json number,title,author,createdAt,reviewDecision,url
```

**Поиск GitHub работает по UTC, отчёт — по локальному дню.** Поэтому берём окно с запасом
и отсеиваем сами, переводя метку в локальную дату:

```bash
date -d '2026-09-02T09:39:30Z' +%F
```

Открытые PR идут в отчёт отдельной строкой: они ждут ревью, и это первый кандидат в
блокеры.

### Незакоммиченная работа

```bash
git branch --show-current
git status --short
git diff --stat
```

Это «в работе», а не «сделано», и в отчёте живёт отдельным разделом. `apps/web/AGENTS.md`
в счёт не идёт — его дописывает сам `next dev`.

### Что задето

Для стендапа важнее не файлы, а последствия. Смотрим пути из диффа:

| Путь                                                      | Что сказать команде                                                                 |
| --------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `apps/api/prisma/migrations/*`                            | новая миграция — остальным нужен `pnpm db:migrate`, затем `db:generate`             |
| `packages/contracts/*`                                    | правка контракта видна сразу API и вебу; правка формы запроса или ответа — ломающая |
| `apps/api/src/modules/*`                                  | какие модули бэкенда и появились ли ручки (тогда и `.claude/docs/api.md`)           |
| `apps/web/src/{views,widgets,features,entities,shared}/*` | какие слои FSD и какие экраны                                                       |
| `CLAUDE.md`, `.claude/*`                                  | изменились правила или процесс — это касается всех                                  |
| `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`   | зависимости: остальным нужен `pnpm install`                                         |

## 3. Формат отчёта

Печатаем в чат; файл создаём только если попросили. Разделы без данных выкидываем целиком,
а не заполняем прочерками.

```
# Стендап за <дата>, <день недели>

## Сделано
- <тема>: <что именно> — <зачем, из тела коммита>. `<sha>`, <N файлов>, <область>

## Влито
- #<N> <заголовок> — влит в <время>, <rebase / merge-коммит>. <url>

## В ревью
- #<N> <заголовок> — открыт <дата>, ревью: <статус>. <url>

## В работе, не закоммичено
- ветка `<имя>`: <что в диффе>, <N файлов>

## Внимание команде
- <миграции, правки контрактов, ломающие изменения, новые зависимости>

## Осталось на потом
- <только из явного источника: «вне объёма» в теле PR, незакрытые пункты в .claude/.plans>
```

- **Группируем по смыслу, а не по коммитам.** Три коммита про один экран — один пункт с
  тремя `sha`. Отчёт читают вслух, список хешей никому не нужен.
- **Каждый пункт опирается на вывод команды.** Хеши, номера PR, числа файлов не
  пересказываем по памяти и не округляем «на глаз».
- **«Зачем» берём из тела коммита и тела PR.** Своих версий о том, зачем делалась задача,
  в отчёт не добавляем.
- **Ссылки на PR — полным URL**, их вставляют в тред стендапа.
- Раздел «Осталось на потом» — только с источником. Нет источника — нет раздела: план на
  сегодня придумывает человек, а не отчёт.

## Чего не делаем

- Не коммитим, не пушим, не мержим, не правим файлы — скилл читающий.
- Не запускаем `pnpm build`, `lint`, `typecheck`: отчёт о вчерашнем дне, а не о текущем
  состоянии сборки.
- Не оцениваем работу и не считаем проценты готовности.
- Не тащим в отчёт коммиты вне периода, чтобы день выглядел плотнее.
- Не выдаём чужие коммиты за свои и наоборот.
