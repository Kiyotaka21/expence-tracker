# Pull request

Процедура одного PR: аргументы → ветка → проверки → тело → `gh pr create` → что вернуть
человеку.

PR открываем только когда попросили. Влитие — отдельный шаг и отдельная просьба.

## 1. Аргументы

```
/pr '<заголовок PR>' [ветка]
```

```bash
/pr 'feat(web): собрать главный экран с меню, профилем и пагинацией'
/pr 'fix(api): починить гонку при ротации refresh-токена' fix/api-refresh-race
```

- **Первый аргумент — заголовок PR** целиком, в кавычках: внутри двоеточие и пробелы.
- **Второй — ветка-источник** (`--head`). Не передана — берём текущую:
  `git branch --show-current`.
- **Заголовок не передан** — собираем сами по коммитам ветки и называем его в ответе перед
  созданием. `--fill` для этого не используем (см. шаг 5).
- **Ветка `main`** — в аргументе или текущая — стоп: PR из `main` в `main` не бывает.
  Сначала ветка и коммиты по скиллу [commit](../commit/SKILL.md).

**Заголовок — по правилам заголовка коммита** (тот же скилл): `<тип>(<область>): <что
делает>`, до 72 символов, императив, с маленькой буквы, без точки в конце. Область — по
преобладающей части диффа: PR, где заодно правились сиды и документация, но основная работа
в вебе, остаётся `feat(web)`, а не теряет область.

Переданный заголовок не переписываем молча. Не по формату — заглавная буква, точка в конце,
длиннее 72 символов, нет области — говорим об этом и предлагаем исправленный вариант.

## 2. Ветка

```bash
git fetch origin --prune
git branch --show-current
git status --short
git log --oneline origin/main..HEAD
```

- **`origin/main..HEAD` пусто** — PR открывать не из чего: работа либо не закоммичена, либо
  уже в `main`.
- **Незакоммиченные изменения** — сначала `/commit`: в PR попадает только запушенное.
  Исключение — `apps/web/AGENTS.md`, его дописывает сам `next dev`.
- **`main` уехал вперёд** — обновляем ребейзом, не merge-коммитом: история линейная.

```bash
git pull --rebase origin main
```

- **Ветка не запушена или есть локальные коммиты сверху** — пушим:

```bash
git push -u origin <ветка>          # первый пуш
git push --force-with-lease         # после ребейза; никогда просто --force
```

- **PR на эту ветку уже открыт** — второй не создаём: правки по ревью доезжают обычным
  пушем, PR обновляется сам.

```bash
GH='/c/Program Files/GitHub CLI/gh.exe'
"$GH" pr list --head <ветка> --state open --json number,title,url
```

## 3. Проверки

CI нет, поэтому единственный барьер перед PR — руки:

```bash
pnpm typecheck && pnpm lint && pnpm build
```

Не проходит — **PR не открываем**: починили и прогнали снова.

Что проверить не удалось — клики в браузере, прогон миграции на чужой базе — не
замалчиваем: это отдельная строка в теле PR.

## 4. Тело

Тело пишем в файл **в скрэтчпаде, вне репозитория** — в индекс он попадать не должен.

Разбивку по коммитам и «зачем» берём из истории ветки, а не по памяти:

```bash
git log --no-merges --format='%h %s%n%n%b' origin/main..HEAD
git diff --stat origin/main..HEAD
```

```markdown
## Что делает

<одним абзацем: какую задачу закрывает PR>

## Коммиты

- `<тип>(<область>): <заголовок>` — <что внутри>

## Решения

- <что выбрано, что отвергнуто и почему — то, чего не видно в диффе>

## Проверки

- `pnpm typecheck`, `pnpm lint`, `pnpm build` — прогнаны
- <что проверить не удалось>

## Вне объёма

- <что осознанно не сделано и почему>
```

- **«Что делает» и «Проверки» обязательны.** Разделы без данных выкидываем целиком, а не
  заполняем прочерками.
- **«Решения» берём из тел коммитов.** В этом репозитории тело обязательно и объясняет
  «зачем»: в PR идёт оно, а не пересказ заголовка другими словами.
- **Ломающее изменение** — отдельной строкой в начале тела, с тем же `BREAKING CHANGE`, что
  в футере коммита. Для `packages/contracts` ломающей считается любая правка формы запроса
  или ответа: её видят сразу оба приложения.
- **Миграции и новые зависимости называем прямо**: ревьюеру нужно знать, что ему предстоит
  `pnpm db:migrate` и затем `pnpm db:generate` либо `pnpm install`.
- **Проверки перечисляем явно.** Умолчание ревьюер прочтёт как «проверено».

## 5. Создание

**`gh` установлен, но не в PATH** — ни Git Bash, ни PowerShell его не видят. Вызываем по
полному пути:

```bash
GH='/c/Program Files/GitHub CLI/gh.exe'
"$GH" pr create --base main --head <ветка> \
  --title '<заголовок из аргумента>' \
  --body-file /path/to/scratchpad/pr-body.md
```

- **`--base` всегда `main`.** Другая база — только если попросили явно.
- **Тело передаём файлом** (`--body-file`), а не `--body`: в теле markdown со списками и
  кодом, в одной строке аргумента оно разъезжается.
- **`--fill` не используем.** Он берёт заголовок и тело из коммита ветки — при нескольких
  коммитах в PR уезжает описание одной части работы вместо описания целого.
- `--draft`, `--reviewer`, `--assignee`, метки — только по просьбе.

## 6. После создания

- **Печатаем URL из вывода `gh`** полностью: его вставляют в тред и открывают на ревью.
- **Правки по ревью** — обычные коммиты в ту же ветку и `git push`. Историю опубликованной
  ветки не переписываем ради красоты; пришлось — `--force-with-lease`.
- **Влитие — отдельная просьба.** Вливаем «Rebase and merge»: коммиты в ветке осмысленные,
  схлопывать их незачем. «Squash and merge» — только для черновой истории с `wip`-коммитами.
- После влития ветку удаляем и на GitHub, и локально — раздел «Ветки» корневого
  [CLAUDE.md](../../../CLAUDE.md).

## Чего не делаем

- PR из `main`, PR в базу, отличную от `main`, второй PR на ту же ветку.
- PR с падающими `pnpm typecheck`, `pnpm lint`, `pnpm build`.
- `--fill` вместо своего заголовка и `--body` вместо `--body-file`.
- Файл с телом PR внутри репозитория.
- Молчание о том, что проверить не удалось.
- Обновление ветки merge-коммитом вместо ребейза и `git push --force` без
  `--force-with-lease`.
- Мерж, назначение ревьюеров и `--draft` без просьбы.
