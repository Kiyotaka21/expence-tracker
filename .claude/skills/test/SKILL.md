# Тест на файл

Процедура одного теста: аргумент → раннер → что вообще тестируем в этом файле → спека →
прогон → коммит.

Тест пишем на переданный файл и только на него. Захотелось заодно покрыть соседей — это
отдельная просьба.

## 1. Аргумент

```
/test <путь к файлу> [что проверить]
```

```bash
/test packages/contracts/src/transaction.ts
/test apps/api/src/modules/transactions/transaction.mapper.ts
/test apps/web/src/shared/lib/redirect.ts 'открытый редирект через //evil.com'
```

- **Первый аргумент — путь к файлу**, от корня репозитория или от текущего каталога.
- **Второй, необязательный, — что именно проверить.** Передан — тест строим вокруг него,
  остальное покрываем по своему усмотрению и говорим, что покрыли.
- **Путь не передан** — не угадываем по последнему диффу: спрашиваем файл.
- **Файла нет или это каталог** — стоп: называем, что нашли по этому пути.

Первым делом читаем файл целиком и определяем пакет — `packages/contracts`, `apps/api` или
`apps/web`. Пакет решает и вид теста, и где живёт спека.

## 2. Раннер

```bash
grep -n 'vitest' package.json apps/*/package.json packages/*/package.json
```

Раннер — **Vitest**, и заведён он пока только в `apps/api`. Файл оттуда — переходим к
шагу 3. Файл из `apps/web` или `packages/contracts` — раннера в пакете нет, и его нужно
завести: это отдельная единица работы и отдельный коммит `build: завести vitest …`, до
теста, а не вместе с ним.

Как это сделано в `apps/api` — образец для остальных пакетов:

```bash
pnpm --filter <пакет> add -D vitest@<точная версия>
```

- **Версия закрепляется точно, без каретки** — как все зависимости репозитория; сейчас это
  `vitest@4.1.11`, тот же пин ставим в новый пакет.
- Скрипты пакета: `"test": "vitest run"` и `"test:watch": "vitest"`.
- Корневой `package.json` и `turbo.json` уже знают про задачу: `"test": "turbo run test"` и
  `"test": { "dependsOn": ["^build"] }` — как `lint` и `typecheck`, потому что
  `@expence/contracts` потребляется из `dist` и без пересборки тест увидит старый контракт.
- Конфиг — `vitest.config.ts` в корне пакета, `test.include: ['src/**/*.spec.ts']`. Для
  `apps/web` там же алиас `@`: `resolve.alias` на `./src`, иначе спеки не разрешат
  `@/shared/...`.
- **Конфиг остаётся `.ts`, а не `.mts`.** С `.mts` уходит предупреждение Vite про
  ESM-конфиг в CJS-пакете, но падает линт: типизированные правила в
  `packages/eslint-config/base.mjs` привязаны к `**/*.ts`, и `.mts` не получает
  `parserOptions.projectService`. Само предупреждение на каждом прогоне — ожидаемый шум.

Что это цепляет в конфигах пакетов:

- **`apps/api` уже настроен**: `tsconfig.build.json` исключает `**/*.spec.ts` и
  `vitest.config.ts`, поэтому `nest build` не тащит их в `dist`, а основной
  `tsconfig.json` их видит — спеки проверяются `typecheck` и линтом.
- **`packages/contracts` не готов**: у него один tsconfig с `rootDir: src`, `outDir: dist`
  и `files: ["dist"]` в package.json — спека из `src` уедет в опубликованный `dist`.
  Разделяем конфиг так же, как в `apps/api`: `tsconfig.build.json` с
  `"exclude": ["**/*.spec.ts"]` для скриптов `build` и `dev`, основной `tsconfig.json`
  остаётся для `lint` и `typecheck` и спеки видит.
- **`apps/web` готов**: `tsconfig.json` включает `**/*.ts(x)` и стоит `noEmit`, спеки
  типизируются и в бандл не попадают.

**Тесты компонентов требуют отдельной обвязки** — `jsdom` и `@testing-library/react`.
Ставим их, только когда пришли именно за тестом компонента, а не «на будущее».

Раннер появился в новом пакете — правим документацию тем же коммитом:
`.claude/docs/developer-guide.md` и `README.md` (где перечислено, в каких пакетах тесты
есть), разделы «Состояние» в корневом `CLAUDE.md` и в памятке этого приложения.

## 3. Что тестируем в этом файле

| Файл                                                        | Что проверяем                                                                                                        |
| ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `packages/contracts/src/*.ts`                               | схема принимает валидный вход и отвергает невалидный, границы, `z.coerce` (сумма — два знака), значения по умолчанию |
| `apps/api/**/*.mapper.ts`                                   | форма контракта: `Date` → ISO-строка, `Decimal` → строка `toFixed(2)`                                                |
| `apps/api/**/*.service.ts`                                  | бизнес-правила: ветки ошибок, чужой ресурс, ротация и отзыв сессий                                                   |
| `apps/api/src/modules/auth/cookies.ts`, гварды, `common/**` | флаги и путь cookie, решение гварда — то, что вызывается без Nest                                                    |
| `apps/web/src/shared/lib/*`, `entities/**/lib/*`            | чистые функции: форматирование сумм и дат, `safeInternalPath`, разбор ошибок API                                     |
| `apps/web/src/shared/api/client.ts`, `proxy.ts`             | поведение вокруг замоканного `fetch`: обновление токена, `ApiError`, редиректы                                       |
| `apps/web/**/ui/*.tsx`                                      | рендер и взаимодействие — только если стоят `jsdom` и Testing Library (шаг 2)                                        |

**Тестировать нечего — говорим об этом прямо**, а не пишем тест ради галочки. Так выглядят
`index.ts` (баррель), `*.module.ts`, `dto.ts` (обёртка `createZodDto` над контрактом),
`ui`-компоненты из чистой разметки. В этом случае называем ближайшую осмысленную цель: у
`dto.ts` — схема в `packages/contracts`, у `*.module.ts` — сервис модуля.

Что не проверяем нигде:

- **не тестируем Prisma, Nest, zod и react-hook-form** — чужие библиотеки уже проверены;
- **не проверяем, что сервис позвал `prisma.transaction.findMany`** с такими-то
  аргументами: это тест реализации, он ломается при любом рефакторинге. Проверяем то, что
  сервис вернул или бросил;
- **не ходим в базу и в сеть.** База поднимается только под e2e, а их в репозитории нет.

## 4. Файл спеки

**Рядом с исходником, имя `<имя файла>.spec.ts`** (`.spec.tsx` для компонента):
`transaction.mapper.ts` → `transaction.mapper.spec.ts`. Это имя уже зашито в
`apps/api/tsconfig.build.json`, поэтому отдельного каталога тестов не заводим.

- **Импорт — относительный, из соседнего файла**: `./transaction.mapper`. В `apps/api`
  path-алиасов нет вовсе, а в `apps/web` правило FSD и так требует ходить внутри среза
  относительными путями.
- **В `packages/contracts` импортируем `./transaction`, а не собранный пакет** — иначе
  перед каждым прогоном придётся ждать пересборку `dist`. В спеках `apps/api` и `apps/web`
  наоборот: контракт берём как `@expence/contracts`, как его берёт продакшен-код.

## 5. Как пишем

Образец — `apps/api/src/modules/auth/auth.service.spec.ts`: стабы Prisma, `UsersService`,
`JwtService` и `ConfigService` собраны там объектами, а сессии живут в массиве в памяти,
поэтому ротацию и отзыв видно по состоянию хранилища.

```ts
import { describe, expect, it } from 'vitest';
```

- **Импортируем `describe`/`it`/`expect` явно**, без `globals: true`: иначе `next build` и
  `tsc --noEmit` не найдут типов, а глобалы придётся объявлять отдельно.
- **Описания по-русски** — как комментарии и коммиты в репозитории. `describe` — имя
  функции или класса, `it` — поведение целиком:
  `it('отдаёт сумму строкой с двумя знаками')`.
- **Одна проверка поведения — один `it`.** Пять `expect` подряд про пять разных правил
  превращаются в один падающий тест без понятной причины.
- **Ошибки проверяем вместе с типом и текстом**:
  `await expect(...).rejects.toThrow(NotFoundException)`. Голый `toThrow()` зелёный и на
  опечатке в импорте.
- **Деньги сравниваем со строкой** (`'1234.50'`), не с числом: наружу API отдаёт строку, и
  тест на число зафиксирует ровно ту ошибку, от которой это правило защищает.
- **Даты фиксируем явно**: конкретный `new Date('2026-01-15T10:00:00Z')` во входных данных
  и ISO-строка в ожидании. `new Date()` в тесте делает его зависимым от дня прогона.
- **Моки — простые объекты, а не фреймворк моков.** Мапперы принимают структурные
  `*Like`-интерфейсы и о Prisma не знают; сервису достаточно подсунуть
  `{ transaction: { findMany: async () => [...] } }` в конструктор.
- **Nest DI в юнит-тестах не поднимаем.** Vitest компилирует esbuild-ом, а он не умеет
  `emitDecoratorMetadata` — `Test.createTestingModule` с инъекцией по типам просто не
  соберёт провайдеры. Конструируем класс руками: `new TransactionsService(prismaMock)`.
  Понадобился настоящий контейнер — это не юнит-тест, и обвязку (`unplugin-swc`) заводим
  отдельной просьбой.

## 6. Прогон

```bash
pnpm --filter <пакет> test
```

- **Зелёный с первого раза — проверяем, что тест не пустой**: ломаем ожидание (меняем
  ожидаемое значение) и убеждаемся, что он покраснел. Опечатка в пути импорта или забытый
  `await` дают зелёный тест, который не проверяет ничего.
- Дальше — обычный барьер репозитория: `pnpm typecheck && pnpm lint && pnpm build`. Спеки
  попадают под типизированный ESLint, и `no-floating-promises` в них ловится так же, как в
  коде.
- **Тест красный, потому что в коде баг** — не подгоняем ожидание под поведение. Говорим о
  находке и спрашиваем, чинить ли код: это отдельная работа.

## 7. Коммит

По скиллу [commit](../commit/SKILL.md): тип `test`, область по пакету — `test(api)`,
`test(web)`, `test(contracts)`.

```
test(api): покрыть маппер транзакций тестами на форму контракта
```

Заведение раннера — отдельный коммит `build: …` перед тестом, вместе с правкой конфигов,
`turbo.json` и документации (шаг 2).

## Чего не делаем

- Тест на файл, в котором нечего проверять, — вместо честного «тестировать тут нечего».
- Проверка вызовов Prisma и других деталей реализации вместо результата.
- Поход в базу, в сеть и в реальный `fetch` из юнит-теста.
- `new Date()` и случайные данные в ожиданиях.
- Сумма как число в ассерте.
- Зелёный тест, который ни разу не видели красным.
- Подгонка ожидания под найденный баг.
- Установка `jsdom`, Testing Library и прочей обвязки «на будущее», без теста, которому она
  нужна прямо сейчас.
