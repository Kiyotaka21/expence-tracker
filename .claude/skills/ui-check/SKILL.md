# Проверка вёрстки на desktop и mobile

Процедура одного прогона: что снимаем → окружение → сессия → ширины → что смотрим →
отчёт → уборка.

Проверяем **вёрстку**, а не логику: раскладку, переносы, обрезки, попадание в границы
брейкпойнтов. Кликами ходим только там, где без них не увидеть экран — логин, открытие
диалога или меню.

**Скилл ничего не коммитит.** Нашли поломку — по правилам шага 7.

## 1. Что снимаем

```
/ui-check [маршрут или что проверить]
```

```bash
/ui-check                       # маршруты выводим из диффа
/ui-check /dashboard            # только один экран
/ui-check 'диалог операции'     # экран плюс состояние, которое надо открыть руками
```

Аргумент передан — проверяем ровно его. Не передан — смотрим дифф и выводим маршруты
сами:

```bash
git status --short apps/web
git diff --name-only apps/web
git diff --name-only main...HEAD -- apps/web
```

| Что изменилось                                           | Какие маршруты снимаем                                                                |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `views/login`, `views/register`, `app/(auth)/layout.tsx` | `/login`, `/register`                                                                 |
| `views/terms`, `views/privacy`, `app/(legal)/layout.tsx` | `/terms`                                                                              |
| `app/(dashboard)/layout.tsx`, `widgets/app-nav`          | `/dashboard` и `/categories` — оболочка одна на три раздела, но активный пункт разный |
| `widgets/month-summary`, `widgets/expense-breakdown`     | `/dashboard`                                                                          |
| `widgets/transaction-list`, `features/transaction/*`     | `/dashboard` и `/transactions`                                                        |
| `widgets/category-list`, `features/category/*`           | `/categories`                                                                         |
| `widgets/create-menu`                                    | `/dashboard`, меню раскрыть кликом                                                    |
| `shared/ui/*`, `app/globals.css`, `app/layout.tsx`       | `/login` и `/dashboard` минимум: примитивы и токены сквозные, задеты все экраны сразу |

- **Изменений в `apps/web` нет вовсе** — говорим об этом и браузер не поднимаем: проверять
  нечего. Правка в `apps/api` или `packages/contracts` вёрстку не задевает, пока не менялась
  форма ответа.
- **Правка только в логике** (`shared/api/client.ts`, `entities/**/api`, хуки без разметки) —
  тоже не наш случай: это тест по скиллу [test](../test/SKILL.md).
- Диалоги, тосты, меню и пустые состояния — это **состояния экрана**, а не маршруты: их
  открываем на том же экране кликом и снимаем отдельным кадром.

## 2. Окружение

Нужен **живой `next dev` на 3000**, за ним API на 4000 и Postgres: `/dashboard`,
`/transactions` и `/categories` без сессии proxy уводит на логин, а данные приходят из БД.

Сначала смотрим, что уже поднято, — второй `pnpm dev` на занятом порту падает, и вы будете
снимать чужую сборку:

```bash
curl -s -o /dev/null -w '%{http_code}' http://localhost:3000/login
curl -s -o /dev/null -w '%{http_code}' http://localhost:4000/api/health
```

Не отвечает — поднимаем в порядке из [README](../../../README.md):

```bash
docker compose up -d
pnpm --filter api db:seed        # демо-пользователь и данные за месяц
pnpm dev                         # web + api + contracts, в фоне
```

- **Запускаем `pnpm dev` в фоне** и ждём в логе строку про 3000, а не по таймеру. Next 16 с
  Turbopack поднимается несколько секунд, и первый заход на страницу ещё компилирует её на
  лету: пустой или недорисованный первый кадр — не находка, а гонка с компиляцией.
- **Порт занят прошлым прогоном** — освобождаем, а не берём другой:
  `Get-NetTCPConnection -LocalPort 3000 -State Listen | Stop-Process -Id $_.OwningProcess`.
- **Прод-сборку для проверки вёрстки не делаем.** Разметка та же, а ждать `next build`
  незачем. Исключение — подозрение именно на сборку: шрифты `next/font`, отсутствующие в
  дев-режиме классы Tailwind.
- **Публичные экраны (`/login`, `/register`, `/terms`, `/privacy`) не требуют ни API, ни
  БД.** Правка только в них — хватит `pnpm --filter web dev` и рядом
  `pnpm --filter @expence/contracts dev`.

## 3. Сессия

Демо-пользователь заведён сидами, креды лежат в `apps/api/prisma/seed.ts`:

```
demo@expence.local / demo12345
```

Логинимся **через форму один раз** за прогон: cookie httpOnly ставит API, руками её из
Playwright не подложить.

1. `browser_navigate` на `http://localhost:3000/login`;
2. `browser_snapshot` — берём ref-ы полей;
3. `browser_fill_form` — почта и пароль;
4. клик по кнопке входа и `browser_wait_for` на текст с дашборда.

Дальше в рамках одной сессии браузера cookie живёт, и по защищённым маршрутам ходим
`browser_navigate` без повторного входа.

- **Кинуло назад на `/login`** — не чините вёрстку: либо сиды не применены, либо API лежит,
  либо истёк refresh. Смотрим `/api/health` и лог `pnpm dev`.
- **Пустые состояния** проверяем на свежем пользователе через `/register`, а не сносом
  сидов: сиды нужны остальным кадрам. Список без операций и кольцо без расходов — это
  отдельные состояния, и снимать их стоит, если правка их задевает.

## 4. Ширины

Раскладка веба переключается дважды, и обе точки — стандартные брейкпойнты Tailwind:

| Граница       | Что меняется                                                                              |
| ------------- | ----------------------------------------------------------------------------------------- |
| `lg` — 1024px | рельса `app-sidebar` (`hidden lg:flex`) ↔ шапка `app-topbar` (`lg:hidden`)                |
| `sm` — 640px  | панель со скруглением и отступом ↔ во всю ширину без радиуса (`sm:p-4`, `sm:rounded-3xl`) |

Обязательный минимум — два профиля:

| Профиль | `browser_resize` | Что должно быть видно                                                         |
| ------- | ---------------- | ----------------------------------------------------------------------------- |
| desktop | 1440 × 900       | рельса слева, панель по центру не шире 1360px, отступы `lg:px-9`              |
| mobile  | 390 × 844        | тёмная шапка вместо рельсы, панель во всю ширину, нет горизонтального скролла |

Правка задевает оболочку, сетку или классы `hidden`/`flex-` — добавляем кадры по обе
стороны границы: **1024 и 1023**, **640 и 639**. Ломается всегда на границе, а не в
середине диапазона.

Порядок на каждый кадр: **сначала `browser_resize`, потом `browser_navigate`** — иначе
страница успевает отрендериться под прошлую ширину.

```
browser_resize            390 × 844
browser_navigate          http://localhost:3000/dashboard
browser_wait_for          текст, который появляется после загрузки данных
browser_take_screenshot   первый экран, как его видит пользователь
browser_take_screenshot   fullPage: true — вся страница целиком
browser_evaluate          проверка переполнения (ниже)
browser_console_messages  level: error
```

**Горизонтальный скролл проверяем числом, а не глазами** — лишние 8px на скриншоте не
видно:

```js
() => ({
  doc: document.documentElement.scrollWidth,
  win: window.innerWidth,
  wide: [...document.querySelectorAll('*')]
    .filter((el) => el.getBoundingClientRect().right > window.innerWidth + 1)
    .slice(0, 10)
    .map((el) => (el.tagName + '.' + el.className).slice(0, 120)),
});
```

`doc > win` — вёрстка переполнена, и `wide` называет виновников. Это первое, что смотрим на
390px, и главная причина проверять мобильную раскладку именно Playwright: у headless Chrome
минимальная ширина окна около 500px, и `--window-size=390` даёт там обрезанный кадр вместо
честной мобильной раскладки — статический харнесс из
[developer-guide](../../docs/developer-guide.md) для мобильных ширин не годится, Playwright
таким не ограничен.

## 5. Что смотрим на кадрах

**Скриншот надо посмотреть.** Он приходит картинкой в ответе инструмента — смотрим на неё;
сохранённый файл при необходимости открываем `Read`. Кадр, который никто не открыл, — не
проверка, а артефакт.

По каждому кадру:

- **Оболочка на своём месте**: ≥1024 — рельса и ни следа мобильной шапки, <1024 — наоборот.
  Обе разом или ни одной — поломка `hidden`/`lg:`.
- **Ничего не уехало за край** и нет пустой полосы справа — сверяем с числом из шага 4.
- **Текст не обрезан и не наложен**: длинная почта в меню профиля, длинное имя категории,
  сумма в семь знаков. Обрезка допустима только там, где `truncate` стоит намеренно.
- **Суммы читаются целиком** — деньги не переносим по строкам и не прячем под `…`: цифру
  видно полностью, иначе это находка.
- **Плитки и карточки не разъехались**: сводка месяца, кольцо расходов с легендой, фильтры
  списка операций — на 390px они складываются в столбец, а не сжимаются в кашу.
- **Контролы нажимаемы пальцем**: у `button` высоты 36px (`default`) и 44px (`lg`), у полей
  и `native-select` — 40px. Всё, что в мобильном кадре ниже 36px, — находка.
- **Пагинация и фильтры списка** на 390px не выпадают из панели.
- **Диалог** (`shared/ui/dialog.tsx`) на мобильной ширине не шире экрана, и его кнопки видны
  без скролла.
- **Консоль без ошибок.** Ошибка гидратации — реальная причина расхождения раскладки, а не
  шум: `suppressHydrationWarning` на `<html>` стоит только под `next-themes` и остальных
  расхождений не глушит.

Оговорка про `fullPage`: рельса — `sticky top-8`, и на кадре всей страницы sticky-элемент
рисуется у верхнего края, а не по центру видимой области. Это артефакт съёмки, а не поломка
вёрстки: о рельсе судим по кадру первого экрана.

**Тёмную тему** снимаем только когда правились токены, `globals.css` или цвета в разметке.
Переключателя в интерфейсе нет, тема идёт от ОС через `next-themes`, поэтому ставим её
руками и перезагружаем страницу:

```js
() => {
  localStorage.setItem('theme', 'dark');
  location.reload();
};
```

В тёмной теме проверяем ровно то, что она ломает: читаемость `--income`/`--expense` и то,
что рельса осталась тёмной — её токены в `.dark` не переопределяются намеренно.

## 6. Отчёт

Печатаем таблицей «маршрут × ширина» и списком находок:

```
/dashboard    1440×900  — ок
/dashboard     390×844  — фильтры списка операций выходят за панель на 24px
/categories    390×844  — ок
```

- **Каждая находка называет место в коде**: файл и класс, из-за которого поехало, а не «на
  мобиле некрасиво».
- **Всё чисто — так и говорим**, без пересказа каждого кадра.
- **Не сравниваем с макетом**, которого нет: судим по правилам дизайн-системы из
  [apps/web/CLAUDE.md](../../../apps/web/CLAUDE.md).

## 7. Что делаем с находками

- **Поломка в той правке, которую только что внесли** — чиним сразу: это та же единица
  работы, и коммит по скиллу [commit](../commit/SKILL.md) уезжает уже с исправлением. После
  правки прогоняем сломанный кадр заново.
- **Поломка была до правки** — не молчим и не чиним заодно: называем её и спрашиваем,
  браться ли. Это отдельная работа и отдельная ветка.
- **Дело в цвете — правим токен, а не класс в разметке**: правило дизайн-системы.

## 8. Уборка

- `browser_close` — закрываем браузер, иначе следующий прогон унаследует ширину и сессию.
- Кадры и логи Playwright пишет в `.playwright-mcp/` в корне репозитория. Каталог в
  `.gitignore` — **скриншоты в коммит не кладём**, они не документация.
- `pnpm dev` из шага 2 поднимали мы — говорим, что он остался в фоне, или гасим его, если
  поднимали только под проверку.

## Чего не делаем

- Не судим о вёрстке по одному кадру: два профиля — минимум, границы — при правке оболочки.
- Не проверяем мобильную раскладку харнессом на headless Chrome: ниже 500px он врёт.
- Не подкладываем cookie руками вместо входа через форму — она httpOnly.
- Не пишем e2e-тесты Playwright: раннера в `apps/web` нет, и завести его — отдельная просьба
  (скилл [test](../test/SKILL.md)).
- Не сносим сиды, чтобы посмотреть пустое состояние: для этого есть новый пользователь.
- Не коммитим скриншоты и не держим их в `.next/static` — сборка этот каталог стирает.
- Не чиним попутно то, что сломалось не в этой правке, без спроса.
- Не отчитываемся «проверено», не открыв ни одной картинки.
